# 核心概念

[English](../concepts.md) · **简体中文** · [文档导航](README.md)

这一篇讲 JI 背后的模型。只想直接用的话，先看 [README](../../README.zh-CN.md) 和 [会话与运行](sessions-and-runs.md)。

<br>

## 四个对象

| 对象    | 负责什么                                    | 入口                   |
| ------- | ------------------------------------------- | ---------------------- |
| Agent   | 模型、工具、插件配置，可供多个会话复用      | `createAgent(...)`     |
| Session | 一段对话的状态和待送达消息                  | `createSession(agent)` |
| Run     | 一次持续到 agent 空闲的执行，包含输出和统计 | `chat.send(...)`       |
| Plugin  | 在固定位置修改行为或观察事件                | `definePlugin(...)`    |

<br>

## 从一条消息看循环

假设用户让 agent 计算 `17 × 23`：

1. **插入输入**：把用户消息写入历史。
2. **决策 → 执行 → 记录**：模型选择计算工具，工具返回 `391`，模型消息和工具结果一起写入历史。
3. **回答 → 记录**：模型给出最终回答，没有工具调用，直接写入历史。
4. **结束**：agent 空闲，没有可送达的消息，Run 完成。

一次运行包含多步。每个完成并写入状态的步骤对应一条 `Turn`；结束检查和被中断的步骤不会生成已写入的 Turn。插件可以修改其中某个环节，例如在 `request` 前补充检索内容，在 `toolCall` 后缩短工具结果。

<br>

## 一步里发生了什么

**步边界**是两步之间的时刻：模型没有在输出，工具也没有在执行。每个步边界上：

```
decide ───┬─ ① input    有要插入的消息？        有 → 记录它们，这一步结束
          │             没有，且 agent 空闲？   → 运行结束
          └─ ② request  调用模型，流出增量（request 钩子可以改这次发送的内容，不改历史）
toolCalls ─ 这一回合的工具调用，并行执行 → toolCall（每次调用）
record ──── 把这一步写入历史 → 各插件的 state.reduce
```

`decide` 决定这一步做什么；`toolCalls` 执行模型回复中的工具调用；`record` 把完成的 Turn 写入状态。没有工具调用的回复会跳过 `toolCalls`。`decide` 返回时工具尚未执行，同一步里所有钩子读取的 `ctx.state` 都是这一步开始前已提交的状态。

agent **空闲**是指：历史为空，或者最后一条是没有工具调用的助手消息。

每个完成并写入状态的步骤恰好产生一条 **Turn**，`record`、`state.reduce`、`Run.turns` 看到的是同一个序列：

| `turn.kind` | 来源                                                   | 对历史的影响   |
| ----------- | ------------------------------------------------------ | -------------- |
| `model`     | 模型回复及其工具结果；最终回答的 `results: []`         | 追加消息和结果 |
| `input`     | 在步边界插入的外部消息（用户、steer、follow-up、插件） | 追加消息       |
| `rewrite`   | `decide` 中间件返回的 `rewriteHistory(messages)`       | 替换整个历史   |

最终回答在运行结束前就已经写入，所以它同样经过 `record`。

<br>

## 一步，三个函数

内核把任何 agent 描述成三个函数：

```
π  policy  : S → D* · (A + R)   决策：先流出若干增量 D，最后给出动作 A 或结果 R
ε  env     : A → D* · O         执行：产生副作用，过程中流出增量 D，最后给出观测 O
δ  update  : S × A × O → S      记录：得到下一个状态（同步、纯）
```

有副作用的都是同一种 `D` 的流，纯的都是普通函数。`unfold` 反复执行「决策 → 执行 → 记录」，直到 policy 给出结果为止，输出是一个惰性的事件流。`extend` 给这三个函数中的任意一个套上中间件，这是扩展 agent 的唯一方式。

<br>

## 三层结构

| 层                    | 职责                                                    | 类型                                                                                                    |
| --------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `@ji.dev/kernel`      | `(π, ε, δ)` 代数、`unfold`、`extend`。与 LLM 和 IO 无关 | 泛型 `S, A, O, R, D`                                                                                    |
| `@ji.dev/llm` agent   | 用 pi-ai 实现 `(π, ε, δ)`，把插件编译成内核中间件       | `S = AgentState`、`O = ToolResultMessage[]`、`D` = 全部事件：模型输出、工具开始 / 更新 / 结束、插件事件 |
| `@ji.dev/llm` session | 驱动 `unfold`，排队外部消息，遇到中断时把一次运行分段   | `Session`、`Run`                                                                                        |

<br>

## 不变量

设计依赖下面几条规则。编写插件时需要遵守；开发检查可以发现其中一部分违规行为。

1. **`record` 和 `state.reduce` 同步且纯**：不读时钟，不发请求。相同的已记录 Turn 可以重建相同的状态；重新调用模型仍可能得到不同回答。开发检查会冻结已提交的状态，并把每个 `state.reduce` 执行两次，发现常见的错误（[详见](plugins.md#开发检查)）。
2. **IO 放在 `decide`、`input`、`request`、`toolCalls` 或 `toolCall` 里，并接上 `ctx.signal`**。例如压缩插件在 `decide` 里用 `ctx.complete` 写摘要，再通过 `rewriteHistory` 把替换交给 `record`。
3. **预期内的工具失败是结果，可重试的失败是异常**：拒绝时返回 `toolError(call, reason)`；重试可能解决的失败就抛出，让外层 `toolCall` 中间件看得到。最终仍未处理的异常会被转成错误结果交给模型。
4. **取消和事件通过 `yield*` 传递**：流式中间件（`decide`、`request`、`toolCalls`、`toolCall`）里写 `return yield* next(...)`，或者用 `before` / `after` / `intercept` / `mapEvents`，取消才能传到 HTTP 请求和工具，内层事件才能到达运行，返回值也不会丢。
5. **被中断的一步不会写入**：状态只在一步完成后才前进。
6. **插件状态存在 `AgentState` 里**：位于 `state.plugins[name]`，跟消息一起保存和恢复。
